# ppapd ロードマップ

## 未決事項

影響の大きい順に並べる。決まったものは要件定義書（[PRD.md](PRD.md)）かアーキテクチャ（[ARCHITECTURE.md](ARCHITECTURE.md)）に反映し、ここから消す。

1. **添付のダウンロードの自動化**: 拡張機能が Outlook の画面の添付のダウンロードを利用者に代わって行えるか（ADR 002）。
2. **ブラウザ連携の実現方式**: Tampermonkey などの UserScript、自作のブラウザ拡張（Manifest V3）と Native Messaging、Outlook アドインのどれにするか。ダウンロードの完了と保存先のパスを知る手段（PRD の F-1.6）は、自作の拡張なら `chrome.downloads` API で得られるが、UserScript には見当たらない。Native Messaging にすれば、PRD の S-1〜S-3 と次の 3 が不要になる。
3. **`Origin` 検証の有効性**: Tampermonkey の `GM_xmlhttpRequest` で送ると、`Origin` ヘッダーが `https://outlook.office.com` にならない可能性がある。ページの `fetch` を使うか、PRD の S-2 をやめて S-3（Bearer トークン）だけにするかを決める。
4. **ダウンロードとメールの対応付け**: リンクを開いた先は別のタブになり、ログイン画面を挟むこともある。どのダウンロードがどのメールのリンクから始まったかを、どう突き止めるか（PRD の F-1.6）。
5. **自動で配送するメールの範囲**: 添付をダウンロードするたびに配送するか（PRD の F-1.6）、`projects` の規則に一致したメールに絞るか。署名の画像ファイルなど、配送したくない添付をどう除くか。
6. **ダウンロードフォルダのファイルの扱い**: 配送した後、ダウンロードフォルダのファイルを消す（移動）か残す（コピー）か（PRD の F-5）。
7. **OneDrive のフォルダ共有リンク**: フォルダをダウンロードすると ZIP にまとめられるという前提（PRD の R-5）を確かめる。
8. **「直近」の範囲**: PRD の F-3.1 で、何分以内、または何通以内を「直近」とするか。待機中の ZIP の記録とパスワード候補をいつ破棄するか。同じ組織で照合するときは候補が増えるので、同じ送信者より短くするか。
9. **API のリクエストとレスポンスの形式**: PRD の §7 にあるエンドポイントの形式を定める。
10. **待機中・失敗・不一致の表示**: PRD の F-2.4 のバッジの色と文言。
11. **Bearer トークンの保存場所**: PRD の S-3 のトークンをデーモン側のどこに置くか。HMAC の鍵と同じく DPAPI で保護するか。
12. **リポジトリ名**: 扱う範囲が PPAP より広くなったので、`ppapd` のままでよいか。
