# ppapd ロードマップ

## 未決事項

影響の大きい順に並べる。決まったものは要件定義書（[PRD.md](PRD.md)）かアーキテクチャ（[ARCHITECTURE.md](ARCHITECTURE.md)）に反映し、ここから消す。

1. **デーモンとのつなぎ方**: ブラウザ拡張からデーモンへ、ループバックの HTTP で送るか、Native Messaging で送るか（ADR 003）。Native Messaging にすれば、PRD の S-1〜S-3 と次の 2 が不要になる。
2. **`Origin` 検証の有効性**: ブラウザ拡張のバックグラウンドから送ると、`Origin` ヘッダーは `https://outlook.office.com` ではなく拡張機能のオリジン（`chrome-extension://…`）になる。PRD の S-2 で照合する値を拡張機能のオリジンに変えるか、S-2 をやめて S-3（Bearer トークン）だけにするかを決める。
3. **ダウンロードとメールの対応付け**: リンクを開いた先は別のタブになり、ログイン画面を挟むこともある。どのダウンロードがどのメールのリンクから始まったかを、どう突き止めるか（PRD の F-1.6）。
4. **自動で配送するメールの範囲**: 添付をダウンロードするたびに配送するか（PRD の F-1.6）、`projects` の規則に一致したメールに絞るか。署名の画像ファイルなど、配送したくない添付をどう除くか。
5. **ダウンロードフォルダのファイルの扱い**: 配送した後、ダウンロードフォルダのファイルを消す（移動）か残す（コピー）か（PRD の F-5）。
6. **OneDrive のフォルダ共有リンク**: フォルダをダウンロードすると ZIP にまとめられるという前提（PRD の R-5）を確かめる。
7. **「直近」の範囲**: PRD の F-3.1 で、何分以内、または何通以内を「直近」とするか。待機中の ZIP の記録とパスワード候補をいつ破棄するか。同じ組織で照合するときは候補が増えるので、同じ送信者より短くするか。
8. **API のリクエストとレスポンスの形式**: PRD の §7 にあるエンドポイントの形式を定める。
9. **待機中・失敗・不一致の表示**: PRD の F-2.4 のバッジの色と文言。
10. **Bearer トークンの保存場所**: PRD の S-3 のトークンをデーモン側のどこに置くか。HMAC の鍵と同じく DPAPI で保護するか。
11. **リポジトリ名**: 扱う範囲が PPAP より広くなったので、`ppapd` のままでよいか。
12. **ブラウザ拡張の配布**: ストアで公開するか、デベロッパーモードでの読み込みだけにするか（ADR 003）。
