# 001. 待機中のメールは中身を持たず参照だけを記録する

- 状態: 提案

## 背景

ZIP メールとパスワードメールは別々に届き、利用者が開く順番も間隔も決まっていない。先に開かれた側は、もう片方が開かれるまで何らかの形で待たせる必要がある。

このとき次の制約が引っ張り合う。

- 暗号化 ZIP とそのパスワードが同じ場所に揃うと、暗号化の意味がなくなる。パスワードを含む本文をディスクに残せば、ZIP と一緒に読まれるおそれがある。
- デーモンは再起動しうる。待機中の情報がメモリにしかなければ、再起動で失われ、利用者がメールを開き直す必要がある。
- デーモンは Outlook on the web に接続しない（Graph API を使わない）。メールを取り直せるのは UserScript だけである。

## 決定

片方のメールしか届いていない間、デーモンは ZIP、本文、パスワードを持たない。記録するのは参照だけとする。

- MessageId、添付 ID、`ConversationId`、受信日時
- ZIP の SHA-256、本文の SHA-256
- 送信者アドレスとドメインの HMAC-SHA256

参照は SQLite に記録する。ペアが揃ったら、デーモンは待機していた側の中身を UserScript に再取得させる。UserScript は取り直した中身と、いま開いているメールの中身を一つのリクエストにまとめて送る。デーモンは SHA-256 で取り直した中身が記録と同じであることを確かめてから解凍する。

## 検討した選択肢

| 選択肢 | 採らない理由 |
| --- | --- |
| 待機中の ZIP とパスワードを SQLite に保存する | ZIP とパスワードが同じファイルに揃い、ディスクに残る。 |
| 待機中の ZIP だけを SQLite に保存し、パスワードはメモリに持つ | パスワードが先に届いた場合にメモリにしかなく、再起動で失われる。ZIP が先なら暗号化されたまま残るが、どちらが先かで扱いが変わり、仕組みが二通りになる。 |
| 待機中の ZIP とパスワードをメモリに持つ | 再起動で失われる。待機が長引くほど、パスワードがメモリに残る時間も長くなる。 |
| 再取得した中身を照合しない | 同じ MessageId で取り直しても中身が同じとは限らず、別の ZIP やパスワードで解凍を試すおそれがある。 |

## 結果

- ZIP、本文、パスワードはリクエストの処理中しかメモリに置かれず、ディスクには残らない。
- 参照は SQLite にあるので、デーモンを再起動しても待機は続く。
- ZIP が先でもパスワードが先でも、同じ仕組みで扱える。
- UserScript が、開いていないメールの添付と本文を MessageId で取得できることが前提になる。この取得は Outlook on the web の内部 API に頼るので、その仕様変更で動かなくなりうる。取得できない場合は、この決定を見直す。
- ペアが揃うたびに、片方のメールを取り直す通信が一回増える。

## 未決事項
