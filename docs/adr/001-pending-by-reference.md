# 001. PPAP の片方が届くまでの待たせ方

- 状態: 採用

## 背景

ZIP メールとパスワードメールは別々に届き、利用者が開く順番も間隔も決まっていない。先に届いた側は、もう片方が届くまで何らかの形で待たせる必要がある。

このとき次の制約が引っ張り合う。

- 暗号化 ZIP とそのパスワードが同じ場所に揃うと、暗号化の意味がなくなる。
- デーモンは再起動しうる。待機中の情報がメモリにしかなければ、再起動で失われ、利用者がメールを開き直す必要がある。
- ブラウザ連携は Outlook の認証トークンを扱わないので、開いていないメールの添付も本文も取り直せない（[ADR 002](002-attachments-via-downloads.md)）。先に届いた側は、届いたときに手元に置いておくしかない。

## 決定

ZIP メールが先に届いた場合、暗号化された ZIP はダウンロードフォルダに置いたまま待たせる。デーモンが SQLite に記録するのは次のものだけとする。

- ダウンロードフォルダの下の ZIP のパスと、その SHA-256
- MessageId、`ConversationId`、受信日時
- 送信者アドレスとドメインの HMAC-SHA256

パスワードメールが届いたら、デーモンは記録したパスの ZIP の SHA-256 が記録と一致することを確かめてから解凍する。

パスワードメールが先に届いた場合、デーモンはパスワード候補を Windows の DPAPI（現在の Windows ユーザーでだけ復号できる暗号化）で暗号化し、メールのメタデータとともに SQLite に記録する。ZIP が届いたら復号して解凍に使い、解凍を試した後に消す。ZIP が届かないまま、ペアリングで「直近」とみなす範囲を過ぎたときも消す。

## 検討した選択肢

| 選択肢 | 採らない理由 |
| --- | --- |
| 待機中は参照（MessageId、添付 ID）だけを持ち、ペアが揃ったらブラウザ連携に ZIP を ID で取り直させる | 添付の取得は Outlook の `Authorization` ヘッダーのトークンで認証されており、トークンを扱わないブラウザ連携からは取り直せない（ADR 002）。 |
| 待機中の ZIP を SQLite にも複製する | ZIP はすでにダウンロードフォルダにあり、複製しても暗号化された同じものが二か所に増えるだけである。 |
| 待機中の ZIP の記録をメモリにだけ持つ | デーモンの再起動で失われる。 |
| 待機中のパスワードをメモリにだけ持つ | デーモンの再起動で失われ、利用者がパスワードメールを開き直す必要がある。 |
| 待機中のパスワードを暗号化せずに SQLite に置く | SQLite のファイルを読める者なら誰でもパスワードを読める。 |

## 結果

- ZIP はパスワードを待つ間、利用者が手作業で PPAP を受け取るときと同じく、暗号化されたままダウンロードフォルダに残る。
- 待機中の記録は SQLite にあるので、デーモンを再起動しても待機は続く。
- 利用者が待機中の ZIP を消したり移したりすると、パスワードが届いても解凍できず、不一致になる。
- 待機中のパスワードは、DPAPI で暗号化された形でディスクに残る。他の Windows ユーザーと、ディスクだけを持ち出された場合からは守れるが、同じユーザーの権限で動くプログラムからは守れない。
