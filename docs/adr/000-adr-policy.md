# 000. ADR の書き方と運用

- 状態: 採用

## 背景

ppapd の要件は要件定義書（`docs/PRD.md`）に、実現の仕方はアーキテクチャ（`docs/ARCHITECTURE.md`）に書く。どちらにも結論しか書かないので、なぜその形なのか、ほかの選択肢をなぜ採らないのかを書く場所が別に要る。

その理由が今も成り立っているかどうかは、後から読む人が判断できなければならない。理由が失われていれば、前提が崩れた決定をそのまま守るか、まだ有効な決定を壊すかのどちらかになる。

## 決定

設計上の決定ごとに、その理由と退けた選択肢を ADR（Architecture Decision Record）として `docs/adr/` に書く。ADR は、決定が有効な間はその現在の姿を表す文書として扱い、決定が変われば書き換える。

### ADR を書く場面

次のどちらかに当てはまる決定を書く。

- 複数の選択肢を比べて一つを選んだ決定
- 後から「なぜこうしたのか」「なぜあれを使わないのか」と問われる決定

コードを読めばわかる実装の都合は書かない。

### 文書の分担

| 書く内容 | 置き場所 |
| --- | --- |
| 何を満たすか（要件） | `docs/PRD.md` |
| どう実現しているか（構成、流れ、データの置き場所） | `docs/ARCHITECTURE.md` |
| なぜそうしているか、なぜほかを採らないか | `docs/adr/` |
| まだ決まっていないこと | `docs/ROADMAP.md` |
| その変更をなぜ行ったか | コミットメッセージ |

一つの決定の理由は、一つの ADR に一度だけ書く。要件定義書とアーキテクチャには結論だけを書き、理由が要る箇所からは ADR を参照する。決定に関わるコミットのメッセージでは、ADR の表題を挙げる。

### ファイル名と番号

- ファイル名は `NNN-英語の短い名前.md` とする。`NNN` は 3 桁の連番で、000 はこの文書、決定の ADR は 001 から始める。
- 番号は再利用しない。表題を書き換えても、ファイル名は変えない。

### 状態

| 状態 | 意味 |
| --- | --- |
| 提案 | 検討中 |
| 採用 | 有効な決定 |
| 取り下げ | 決定をやめた。理由を本文に書く |

「未決事項」の節が空になるまで、採用にしない。

### 決定を変えるとき

ADR を書き換えて、いま有効な決定を表すようにする。置き換えられた設計は「検討した選択肢」へ移し、採らなくなった理由を添える。以前の文面は Git の履歴に残るので、ADR を新しく作って古いものを置き換える形はとらない。

ADR に日付は書かない。いつ書かれたかは Git が記録している。

### 書式

```markdown
# NNN. 表題

- 状態: 提案 | 採用 | 取り下げ

## 背景

決定が要る状況と、互いに引っ張り合っている制約。

## 決定

選んだもの。

## 検討した選択肢

| 選択肢 | 採らない理由 |
| --- | --- |

## 結果

この決定で得るもの、払うもの、見直すきっかけになる条件。

## 未決事項

採用の前に決めること。採用時には空にする。
```

## 検討した選択肢

| 選択肢 | 採らない理由 |
| --- | --- |
| 要件定義書に理由も書く | 要件定義書は結論を探す人が読む文書であり、理由が混ざると結論が埋もれる。 |
| コミットメッセージだけに理由を書く | 一つの決定が複数のコミットにまたがると理由が散らばり、履歴をたどらないと行き着かない。 |
| 採用した ADR を凍結し、変更は新しい ADR で置き換える | いま有効な決定を知るのに、置き換えの連鎖をすべてたどる必要がある。以前の文面は Git の履歴で足りる。 |

## 結果

- 決定の理由と退けた選択肢が、決定ごとに一か所にまとまる。
- 決定を変えるときは、ADR を書き換える手間がかかる。

## 未決事項

なし。
