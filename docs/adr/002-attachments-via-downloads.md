# 002. 添付は Outlook の画面からダウンロードさせて受け取る

- 状態: 採用

## 背景

ブラウザ連携は、メールの添付をデーモンへ渡す必要がある。添付の中身を手に入れる道は二つある。一つは、Outlook on the web が内部で使う API を拡張機能が直接呼ぶこと。もう一つは、Outlook の画面のダウンロードで保存されたファイルを受け取ることである。

次の制約が引っ張り合う。

- Microsoft Graph API とアプリ登録は使わない。Outlook on the web の内部 API は公開されておらず、予告なく変わる。
- Outlook.com（20261030007.22）は、添付の取得（`GetFileAttachment`）を `Authorization` ヘッダーのトークンで認証している。Cookie だけで同じ URL を取得すると HTTP 400 になる。観察の詳細は `poc/FINDINGS.md` にある。
- 拡張機能の `chrome.downloads` API は、ダウンロードの完了と保存先の絶対パスを知らせる。
- ページのスクリプトから添付の要素をクリックすると、Outlook は利用者が操作したときと同じく添付を取得して保存する。ZIP は添付そのもの、PDF などは添付の「その他の操作」メニューの「ダウンロード」をクリックする。
- Chrome は、一つのサイトが 2 つ目以降のファイルをダウンロードしようとすると、利用者に許可を求める。許可されるまでダウンロードは保存されずに止まり、ページのスクリプトからも `chrome.downloads` からも止まっていることはわからない。

## 決定

ブラウザ連携は Outlook の認証トークンを扱わない。添付は、ブラウザ連携が Outlook の画面の添付をクリックしてダウンロードさせ、ダウンロードフォルダに保存させる。そのうえで、その保存先のパスとメールのメタデータをデーモンへ渡す。デーモンはダウンロードリンクの経路と同じく、ダウンロードフォルダの下のファイルとして受け取る。

## 検討した選択肢

| 選択肢 | 採らない理由 |
| --- | --- |
| 拡張機能が Outlook のトークンを横取りして `GetFileAttachment` を呼ぶ | Outlook の認証情報を拡張機能が預かることになる。トークンの得方も API の形も公開されておらず、Outlook の更新で動かなくなる。 |
| ページの中で Outlook の `fetch` や `XMLHttpRequest` を差し替えて応答を横取りする | Outlook は開いたことのあるメールをキャッシュから表示し、通信の一部はページの外から出ているため、必要な応答を確実には捕まえられなかった。 |

## 結果

- 添付もダウンロードリンクも、ダウンロードフォルダを経由する一つの道で受け取れる。
- 利用者は添付ごとにダウンロードする必要がない。代わりに、セットアップで一度、Outlook のサイトに Chrome の自動ダウンロード（複数ファイルのダウンロード）を許可する必要がある。許可がないと 2 つ目以降の添付は保存されずに止まり、ブラウザ連携はそれを検知できない。
- 添付の要素の探し方とクリックの手順は、Outlook の画面の作りに依存する。Outlook の更新で画面が変わると動かなくなる。
- 添付は、配送されるまでダウンロードフォルダにファイルとして残る。
- 開いていないメールの添付は取得できない。添付を後から取り直すには、そのメールを開いてもう一度ダウンロードする必要がある。
